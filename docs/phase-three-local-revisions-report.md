# Stage 3 verification: local revisions and guarded medical edits

This report distinguishes the implemented, tested slice from write paths that still need a version contract. It is not a claim that every synchronized entity now has complete concurrency protection. Phase-one sync/backup barriers and the phase-two recovery register remain active. No recovered item was applied to a business table, no device mode/API destination changed, and no inter-device transport was started.

Historical `sync_changes` rows keep null links. The downgrade intentionally refuses to discard evidence.

## Transaction and API behavior

For a protected worker or visit update, the server authenticates and applies the existing checks (visit role/workspace; worker delete password). Fine-grained worker workspace authorization remains a gap. It then reserves `operation_uuid`, performs `UPDATE ... WHERE version = :expected` (or worker `sync_version`), adds the linked revision and **the existing** `SyncChange`, stores the response receipt, and commits once. A retry with the same UUID and request fingerprint returns that receipt. Reuse with different content or actor is rejected. Direct conditional SQL deliberately bypasses the ORM journal; the service writes exactly one explicit event. ORM operations use only the listener. Failure of a revision or event insert rolls back the medical update and receipt.

On stale version, the failed transaction is rolled back before a separate `local_edit_attempts` transaction stores the original request, actor, expected/observed version and reason. HTTP 409 includes `attempt_saved=true` only after that commit. If attempt storage fails, the server returns `EDIT_ATTEMPT_NOT_SAVED`; the UI retains the form and pending retry UUID. Own-attempt GET endpoints are `/medical-visits/edit-attempts/{uuid}`, `/medical-visits/{id}/edit-attempts`, and `/workers/edit-attempts/{uuid}`; another user receives 403 on direct lookup. No attempt endpoint applies the content medically.

The frontend stores only a request SHA-256 and operation UUID under `medical_visit_pending_operation:*` in localStorage, keeps the same UUID for an identical retry, rotates it on changed content, and removes it after an acknowledged success. Phase-two browser capture now includes this metadata prefix as context without deleting it. The active medical-file workflow checks an existing visit before updating the worker snapshot, so a stale visit does not first overwrite `medical_file_data`. These remain two HTTP transactions: if the visit succeeds and the worker later fails, the UI says explicitly that the visit succeeded but the worker save failed. A combined save boundary remains required for all-or-nothing behavior. UI form state is kept on 409 and does not auto-load the server copy. Diagnostic `console.log` statements exposing medical form/response data were removed from `WorkerMedicalFilePage.tsx`.

## Old clients, rollback, and readiness

Old clients that create a worker/visit without `X-Operation-UUID`, or update/delete a protected worker/visit without both required headers, receive a clear 422 validation error and do not write. Other synchronized routes retain their older contracts and remain a material gap. This build must not be pointed at an unmigrated clinic database: ordinary ORM writes now depend on the new tables and `sync_changes` columns. Migration and staged-client rollout are prerequisites; they were not performed on clinic data.

Rollback must retain `local_revisions`, `sync_changes`, `local_write_operations`, and `local_edit_attempts` and must preserve the phase-one guards. Reverting code to an old writer against a migrated database would re-enable unversioned overwrites and create unlinked events, so it is not a safe operational rollback. A safe fallback is read-only operation for affected writes while keeping the evidence tables and pending source storage intact. The Alembic downgrade refuses evidence deletion.

The stage-three core is ready for **further review and expansion within this stage**, not for phase four or clinical deployment. Remaining stage-three work includes expected-version/idempotency contracts and concurrency tests for other synchronized medical/administrative entities and batch assignment routes, a combined worker/visit save boundary, robust signed-document fixtures, and a safe replacement for suspended import confirmation. No transport engine was started and no sync barrier was lifted.

### Active contracts and frontend behavior

No additional business entity was made active in this pass. The only active protected mutation consumers remain `medicalVisitsApi.ts` and `workersApi.ts`; they already persist a request fingerprint and UUID, reuse the UUID for the same request, send the appropriate version, and delete metadata only after acknowledged success. All newly classified remaining routes are **suspended**, so adding operation/version headers to their clients would falsely imply protection. Their existing consumers receive the stable 423 error through the shared `api/axios.ts` interceptor, which converts it to the non-retryable safety error and does not refresh/retry it. Forms reset only after awaited success in the inspected consumers; no broad UI redesign was made.

The creation contract has no `expected_version`: it requires `X-Operation-UUID`; the server fingerprints the create payload, reserves a durable receipt before the ORM insert, commits entity + initial revision + existing `SyncChange` + result receipt together, returns the stored result for a lost-response retry, and rejects the same UUID from another actor or with different content. Update/delete/state operations require both headers. Batch operations have no partial-result contract yet and are suspended as a whole.

### Baseline and dependency verification

`baseline_batch` remains content-free and keyset/batch resumable. On a synthetic old visit, two invocations left exactly one baseline at the observed version, no invented `SyncChange`, and unchanged medical JSON. No clinic baseline was run.

The HTTP test failure was traced to project dependency metadata, not guessed from the import text. Installed Starlette `1.7.0` declares `httpx2>=2.0.0` for its `full` extra and its `TestClient` imports `httpx2` first. The project had no Python lock and `backend/requirements.txt` omitted any test client. `backend/requirements-test.txt` now records `httpx2>=2.0.0`; version `2.13.1` was installed in the workspace virtualenv. No runtime production dependency was replaced.
